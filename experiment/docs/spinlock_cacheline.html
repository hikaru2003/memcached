memcached の spinlock と cacheline の独立性

memcached の spinlock は item_lock という pthread mutex の配列で管理される。 スピン中の PAUSE 挿入回数 N と QPS の関係を分析するにあたり、 「ロックを取ったら item データも自動的にキャッシュに乗るのか？」という直感的な疑問が生じる。 本資料はこの疑問への回答として、 ロックの cacheline と item データの cacheline は完全に独立している ことを図解で説明する。

1. 前提知識: MESI プロトコル

Intel CPU は各 L1/L2 キャッシュラインに MESI 状態を持たせて、 複数コア間のキャッシュ整合性を保つ。cacheline は 64 バイト単位で管理される。

状態意味他コアが同じ line を持てるか
M (Modified)このコアだけが持ち、DRAM と内容が違う (書き換え済み)否 (invalidate 済み)
E (Exclusive)このコアだけが持ち、DRAM と内容一致否
S (Shared)複数コアが同一内容を持てる可
I (Invalid)無効 (使えない、再取得が必要)—
重要な性質: M 状態を持てるのは常に 1 コアだけ。 書き込み (LOCK CMPXCHG, mov store 等) は M 権を要求し、 他コアの同 line を invalidate する必要がある。これが cacheline 争奪の原因。

2. memcached が触る cacheline の内訳

単一 key ワークロード (SET/GET を key = "1" だけで発行) を考える。 memcached が 1 リクエスト処理中に触る主なメモリ領域は 4 種類ある。 これらは物理的に別の場所にあり、それぞれ独立した cacheline を占める。

図 1: memcached が 1 リクエストで触る主な cacheline (概念図、物理レイアウトは実装依存)

3. trylock が M にするのはどの cacheline か

pthread_mutex_trylock() の内部実装は LOCK CMPXCHG (Compare-And-Swap の LOCK-prefix 版) を使う。 この命令が要求するのは ロック変数のアドレスを含む cacheline (= A) だけ。 item データや LRU の cacheline (B/C/D) は一切触らない。

図 2: trylock が M にするのは item_lock の cacheline A だけ

4. クリティカルセクション実行中の cacheline pingpong

ロックを取ったコア X が CS 内で実行する典型的な操作を追う。 

// X が spinlock_lock(item_lock) 成功後 (cacheline A: M on X)
item = do_item_get(key);         // ← ここで cacheline B を触る
item->flags |= FLAG_UPDATED;      // ← cacheline B を書き換え
do_item_update(item);            // ← ここで cacheline C (LRU) を更新
stats.get_hits++;                // ← cacheline D を更新
spinlock_unlock(item_lock);      // ← cacheline A を書き換え
図 3: CS 実行中に各 cacheline がどう推移するか (4 コアの単一 key 高競合ワークロード)
ポイント: ロック cacheline (A) を保持している間に、item cacheline (B) や LRU cacheline (C) を触ると それぞれ別の RFO が発生する。ロック獲得コストとは別に、CS 内で毎回 cacheline move が起きる。

5. スレッド数増加の影響

スレッド数が増えると cacheline を奪い合う相手のコア数 が増える。 これは A (lock) だけでなく B (item), C (LRU), D (stats) にも影響する。

スレッド数cacheline A の争奪cacheline B/C/D の争奪CS 長への影響
1争奪なし (常に M on 自分)争奪なし最小 (L1 hit)
22 コア間 pingpong2 コア間 pingpong小
44 コアで奪い合い4 コアで奪い合い、待ち行列発生中
88 コアで奪い合い、L3 帯域に近づく8 コアで奪い合い、より深刻大
今回の実験: スレッド数 = 4 固定で PAUSE 回数 N を sweep する。 そのため上記の「スレッド数依存」の効果は N の間で共通しており、N 感度としては現れない。 唯一 N が影響するのは、trylock の頻度が下がることで cacheline B/C/D の pingpong 頻度もわずかに下がる 副次効果。

6. False sharing のケース (参考)

もしロック変数と item データが 同じ cacheline に載っていた ら、 trylock で M 権を取った瞬間に item cacheline も自動的に M になる (光の直感的な理解が正しくなる状況)。 これを false sharing と呼ぶ。

図 4: 正常な設計 vs false sharing の比較

memcached は item_locks[] を独立配列にしており、item データとは別領域なので false sharing は起きない。 これは意図的な設計であり、ロック競合と item データ競合を独立に分析できる利点がある。

7. 実験への示唆

hold time (CS 長) 実験

  • CS 長 = cacheline B/C/D の move 時間を含む
  • L1 hit 前提の理論最小値 (数十 cy) より必ず大きくなる
  • 予想: 数百 cy 〜 1k cy オーダー (skylake の HITM 転送コスト ~50-80cy を複数回)
  • N を変えても命令数は変わらないので median CS 長は N に対してほぼフラットになるはず

unlock latency 実験 (既に実施済み)

  • unlock latency = cacheline A を再取得する時間 + atomic store + (futex_wake if any)
  • 実測: N=0 で p99 = 1.7 μs (= 3570 cy)、N=200 で p99 = 0.2 μs (= 420 cy)
  • N が大きくなるほど他コアの trylock 頻度が減り、A の pingpong 頻度も減る → 単調減少

QPS 山形の解釈

  1. 左側 (N=0→4): PAUSE 増 → A の pingpong 減 → unlock latency 減 → CS 全体が早く終わる → QPS 改善
  2. 右側 (N=4→200): A の pingpong はさらに減るが、trylock 間隔 (N × PAUSE cy) が CS 長を超え始める → 解放後の空振り時間が増えて QPS 悪化

この解釈の検証には CS 長を実測して、trylock 間隔と交差する N を予測 → 実測 QPS ピーク N と一致するか確認する必要がある。
