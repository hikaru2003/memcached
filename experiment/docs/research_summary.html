1. 研究背景と目的

1.1 背景

データセンタでは複数世代の CPU アーキテクチャが混在して稼働しているが、アプリケーションはアーキテクチャの違いを考慮せず同一設定で動作している。特に PAUSE 命令 の実行サイクル数はアーキテクチャによって最大 12 倍以上異なる:

アーキテクチャPAUSE 実行サイクル (-O2 実測)
Broadwell~10 cy
Ice Lake~39 cy
Emerald Rapids~37 cy
Skylake~124 cy (異常に大きい)

1.2 研究目的

目的: memcached のスピンロックにおいて、PAUSE 挿入回数 N とスループット QPS の関係を、 以下の 2 つの視点から明らかにする:
  1. アーキ間比較: 同じアプリケーション設定で、アーキごとに最適 N と挙動がどう違うか
  2. 単一アーキ (Skylake ann) 詳細: PAUSE 回数を変化させた時のスループットとレイテンシの関係、そのメカニズムは何か

研究結果A 複数アーキ間比較

研究の問い: 同じアプリケーション設定 (memcached, スピンロック実装, ワークロード) で、 異なる CPU アーキテクチャを走らせた時、スループットや最適 PAUSE 回数はどう変わるか？

A.1 各アーキの PAUSE 実行サイクル数

まず基本情報として、各アーキで PAUSE 命令が消費するサイクル数を単体実測 (pause_cycle_count.c を -O2 コンパイル、taskset で 1 コアに固定して測定)。単一の代表値なので表で提示する。

アーキPAUSE cybase clockPAUSE 実時間

Ice Lake38.74 cy2400 MHz16.1 ns
Emerald Rapids37.16 cy--
Skylake124.20 cy2100 MHz59.1 ns (最も長い)
ここから伝えたい主張: Skylake は他アーキの 3〜12 倍長い PAUSE サイクル。 同じ N でも実際のスピン待ち時間 (絶対時間) は大きく異なる。この事実が、以降の「アーキごとに最適 N が違う」議論の前提となる。

この 2 図から得られる本質的な観察: N=0 (PAUSE を全く挟まない tight spin) でも各アーキで handoff latency に差がある (p50: Ice 614 / Emerald 634 / Broadwell 800 / Skylake 890 cy)。 PAUSE の影響が無い条件で差があるということは、PAUSE cycle 以外のアーキ固有の要因が存在する。 これは前セクション (A.2) の「PAUSE budget での正規化でも Emerald だけ突出」という観察と整合的。

※ この要因の正体は次の A.4 分析セクションで扱う (cache_miss 実験による RFO 量での説明を試みた結果、 RFO 量では説明できないことが判明した)。

A.4 分析と考察

結果1: 最適 N は PAUSE サイクル数に反比例する

Skylake (124 cy) は N が小さくても十分なスピン時間を確保できる → 少ない N で peak。 逆に Broadwell (10 cy) は十分なスピン時間を確保するには N を大きくする必要がある。

実用的示唆: 同一の N 設定を全アーキで使うのは非最適。 アーキごとに PAUSE サイクル数に応じた N 調整が必要。

結果2: N=0 の handoff latency にアーキ差がある

N=0 (tight spin、PAUSE を全く挟まない条件) でも handoff latency にアーキ差がある:

アーキTSC (MHz)N=0 handoff p50 (cy)N=0 handoff p50 (µs 参考)
Ice Lake (Sunny Cove)24006140.256
Emerald Rapids21006340.302
Broadwell24008000.333
Skylake21008900.424
ここから確実に言えること: N=0 では PAUSE の影響がないため、 PAUSE cycle 数以外にアーキ固有の要因が handoff latency に影響している。 差の絶対値は最大 1.45 倍 (Ice Lake 614 → Skylake 890 cy)。

その要因は何か? — RFO 量では説明できないことが判明

要因候補の一つとして cacheline 争奪 (RFO) を疑い、cache_miss sweep 実験で各アーキの RFO/req を実測した。もし「RFO が多いアーキ = handoff latency が長い」ならば、RFO 量が要因と特定できる。

アーキN=0 handoff p50 (cy)N=0 RFO/req (実測)相関
Ice Lake614~10整合
Emerald Rapids634~10整合
Broadwell80030-50 (Ice/Emerald の 3-5 倍)整合
Skylake89030-50 (Broadwell と同程度)整合
サイクル換算での再解釈: 元は µs 単位で「Broadwell と Emerald が近い (0.305 vs 0.303 µs) のに RFO 量が違うから RFO では説明できない」と結論していた。しかし各アーキで動作周波数が異なるため (Broadwell 2.4 GHz / Emerald 2.1 GHz)、サイクル数で見ると Broadwell 800 cy vs Emerald 634 cy と有意な差があり、この差は RFO 量の差と方向性が一致する (RFO 少 → cy 少、RFO 多 → cy 多)。

→ サイクル換算では RFO 量と handoff cy の間に正の相関が見える。ただし RFO 量の絶対値は アーキ間で 3-5 倍差なのに handoff cy 差は 1.4 倍程度なので、RFO は要因の一つだが単独では 差の大きさを完全には説明できない (他要因: L3 topology, ring vs mesh, cacheline transfer レイテンシ等)。

つまり「アーキ固有の要因が存在する」ことは確定したが、 その正体は今回の一連の実験では 特定できていない (要今後検証)。

研究結果B Skylake ann 単体詳細分析

研究の問い: 1 つのアーキ (Skylake ann) に絞って、PAUSE 回数 N を変化させた時に QPS 山形が発生するメカニズムは何か？

B.1 unlock latency 実験

実験内容

pthread_mutex_unlock の実行時間を測定。この時間は「ロック cacheline (item_lock の変数) の M権を再取得するまでの時間」を含み、他コアの trylock による cacheline 争奪の激しさの指標になる。

static inline void spinlock_unlock(spinlock_t *sl) {
    uint64_t t1 = rdtsc();
    pthread_mutex_unlock(&sl->mutex);   // M権再取得 + store + (futex_wake if needed)
    uint64_t t2 = rdtsc();
    spinlock_record_unlock(t2 - t1);
}

結果: N とともに unlock latency は単調減少

このグラフを載せる目的: unlock latency (= ロック cacheline の M権再取得コスト) が N の増加に対して単調に減少すること、特に N=0 → N=4 の急降下が大きいことを示すため。この形が次の「QPS 山形の 3 段階解釈」の根拠になる。

主軸に mean を使う理由: QPS (= 平均スループット) の山形を説明する指標としては、tail 値 (p99/p999) より mean が理論的に適切 (QPS ≈ 4 workers / 平均 request 処理時間 で直接対応する)。tail は参考として併記する。

このグラフから読み取れる重要な事実 (mean 基準):
  • N=0 → N=4: mean が 0.29 → 0.13 µs (2.2倍改善) → 一番大きな変化はこの区間で発生
  • N=4 → N=10: mean が 0.13 → 0.11 µs (微減) → 改善が飽和
  • N=10 → N=200: mean が 0.11 → 0.05 µs (緩やかに継続減少)
この 3 段階の変化パターンが、次の QPS 山形の 3 段階解釈の直接の根拠となる。

このグラフを載せる目的: QPS 山形と unlock latency の関係を 1 枚で見せることで、両者の対応関係 (どこまで unlock で説明でき、どこから説明できないか) を明確にするため。

Stage 1 の解釈は変わらない: mean unlock latency の 2.2 倍改善 (0.29→0.13µs) が QPS 17% 改善に寄与。 Stage 3 の 不整合の性質: mean は 0.11→0.05µs の 60ns 改善しかしていないのに、 QPS は 26% 悪化 (960→712k)。60ns の unlock 改善では説明できない大きな悪化 → 別要因の存在を示唆。

B.3 補助データ: futex 落ち回数の激減

このグラフを載せる目的: Stage 1 (N=0 → N=4 の QPS 急上昇) を支える別の要因として、 futex syscall 回数の激減があることを示すため。

実験内容: spinlock で 30 rounds トライしても取れない場合、futex にフォールバックしてスリープする。この futex syscall 発行回数 (per request) を N 毎に測定。

B.4 補助データ: RFO (バス競合) の変化

このグラフを載せる目的: cacheline 争奪 (RFO/req) の減少が QPS 改善に寄与するか、 どの Stage で効いているかを見るため。
RFO の詳細は rfo_explanation.html を参照。

実験内容: offcore_requests.demand_rfo (perf イベント) で 1 リクエストあたりの RFO 数を N 毎に測定。

測定範囲の注意: offcore_requests.demand_rfo はコア単位の 集計値で、 特定のアドレス/ロックには絞れない。つまり以下すべてが混ざっている:
  • spinlock (item_lock / slabs_lock) の LOCK CMPXCHG
  • pthread_mutex_unlock の atomic store
  • item refcount の incr/decr
  • hash table pointer 更新、LRU list 更新、stats カウンタ 等
本実験ではこれらの 総和のみを扱い、内訳 (どのロック由来か、item_lock と slabs_lock の比率など) は特定していない。

B.6 分析と考察

Stage 1 (N=0 → N=4): 急上昇の説明

メカニズム:
  • N=0 では 30 rounds 連続で trylock を叩く → ロック cacheline (A) を全 worker が奪い合う → pingpong 激しい
  • PAUSE を挟むと trylock 頻度が下がる → cacheline A の争奪頻度減 → unlock 時の M権再取得コスト大幅減
  • 結果: unlock latency p99 が 1.72µs → 0.34µs (5倍改善) → 全 request の処理時間短縮 → QPS 急上昇

Stage 2 (N=4 → N=10): plateau の説明

Stage 1 の改善が飽和。unlock latency の変化が緩やか (0.34 → 0.32 µs) で、QPS もほぼ横ばい。両者の相関が維持されている。

Stage 3 (N=10 → N=200): 緩やかな低下 — handoff latency の悪化で説明可能

説明: この範囲では unlock latency はさらに改善しているのに QPS 悪化。 これは unlock latency 以外の遅延要素の存在を意味する。 その正体は handoff latency (release → 次スレッドの trylock 成功 までの時間) の悪化 と考えられる。ann 単独データで見ると Skylake の handoff は N=10 付近で最小、以降 U 字型に悪化する:
図 B.6: Skylake ann の handoff latency vs N (p50 (青、左軸) / p99 (橙、右軸) / p99.9 (赤、右軸))。p50 は N=10 で最小 (738 cy)、以降緩やかに悪化。
ann の具体的な数値 (サイクル、TSC=2100 MHz):
  • N=0: p50 = 890 cy, p99 = 15617 cy, p99.9 = 15617 cy
  • N=10: p50 = 738 cy (最小), p99 = 11977 cy
  • N=100: p50 = 838 cy, p99 = 17142 cy
  • N=200: p50 = 837 cy, p99 = 18124 cy, p99.9 = 30229 cy (N=10 比 2.5倍悪化)
メカニズム: N が大きい → PAUSE ループ中に unlock が発生する確率が高い → 次の trylock 実行まで 平均 N × PAUSE_cy / 2 の空振り時間が積み重なる → handoff latency が悪化 → QPS 低下。

unlock latency と handoff latency の切り分け:
  • unlock latency: 「pthread_mutex_unlock の実行時間」= M権再取得コスト → N とともに単調減少
  • handoff latency: 「release → 次獲得」= 上記 + PAUSE 待ち + trylock 実行 → U字型 (N=10 で最小)
両者は別の遅延要素で、Stage 3 の悪化は handoff (特に PAUSE 待ち部分) が支配的。

6. わかったこと / 未解明の点

6.1 わかったこと

  1. アーキ間で最適 N は大きく異なる (PAUSE サイクル数に反比例する傾向)
  2. N=0 の handoff latency にもアーキ差がある (PAUSE 以外の要因の存在)
  3. Skylake ann の QPS 山形は 3 段階に分解できる:
    • Stage 1 急上昇 = unlock latency mean の 2.2倍改善で説明
    • Stage 2 plateau = unlock latency mean 微減で維持
    • Stage 3 緩やかな低下 = handoff latency の悪化で説明可能 (既存の handoff_sweep データより)
  4. unlock latency と handoff latency は別の遅延要素: unlock は N 単調減少、handoff は U 字型

6.2 未解明の点

  1. N=0 でのアーキ間 handoff 差の要因 (RFO 量では説明できないことが実測で判明)

7. 今後の方針

7.1 短期 (次に実験すべき)

  1. 他アーキ (Broadwell / IceLake / Emerald) での Stage 分析
    • Skylake で観察された 3 段階構造が他アーキでも同じか
    • アーキごとに Stage 1/2/3 の境界 N がどうシフトするか
    • 特に handoff latency の U字型 (最小位置) と QPS peak N の対応関係
  2. unlock latency vs handoff latency の関係整理
    • 両者は別の遅延要素 (unlock は M権再取得、handoff は PAUSE 待ち + 再取得)
    • QPS 山形の左側は unlock 改善、右側は handoff 悪化、が主要因の仮説を数値で裏付け

7.2 長期 (研究成果としての方向性)

  1. アーキ特性から最適 N を予測する理論式の構築
  2. アプリケーション実装での PAUSE 動的調整の実現可能性
