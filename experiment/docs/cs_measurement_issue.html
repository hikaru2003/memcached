CS 長測定の実態と問題点

Phase 1・Phase 2 で測定した「クリティカルセクション長 (CS 長)」の内容を再確認したところ、 複数種類のロックの CS 長が混合されて計測されている ことが判明した。 これは光の元の仮説 (item_lock の獲得競争と self-service パターン) の検証には 不十分である。本資料は測定内容・問題点・次のアクションを整理する。

目次
  1. 実装: どこで何を測定していたか
  2. memcached の spinlock は 2 種類ある
  3. 実測データから読み取れる CS の内訳

1. 実装: どこで何を測定していたか

Phase 1・Phase 2 で使ったバイナリ (memcached_hold_debug) では、 spinlock.h の spinlock_lock / spinlock_unlock に rdtsc 計測を仕込んでいた:

static inline void spinlock_lock(spinlock_t *sl) {
    for (int round = 0; round < 30; round++) {
        if (pthread_mutex_trylock(&sl->mutex) == 0) {
            tl_lock_start = _rdtsc();   ← 開始点
            return;
        }
        for (int p = 0; p < N; p++) cpu_relax();
    }
    pthread_mutex_lock(&sl->mutex);
    tl_lock_start = _rdtsc();
}

static inline void spinlock_unlock(spinlock_t *sl) {
    spinlock_record_hold(_rdtsc() - tl_lock_start);  ← delta 記録
    pthread_mutex_unlock(&sl->mutex);
}

つまり計測しているのは trylock 成功後 → pthread_mutex_unlock 直前 の rdtsc 差分。 これは光の元の理解通り (「1 回の lock 保持時間」)。

問題の芽: spinlock_lock / spinlock_unlock は memcached 内の全ての spinlock 使用箇所で共通に呼ばれる。 特定のロックだけを計測する仕組みになっていない。

2. memcached の spinlock は 2 種類ある

ソースコードを確認したところ、spinlock_t の定義と使用箇所は以下:

ロック宣言箇所用途使用回数
item_locks[]thread.c: 配列 (ハッシュで割り振り)item アクセス保護SET/GET ごとに 1 回
slabs_lockslabs.c: グローバル 1 個slab allocator 保護SET 時の allocate/free、GET 時の統計参照など多数

単一 key ワークロード (SET/GET 50%) での競合パターン

図 1: 1 request 処理中に複数種類の spinlock が呼ばれる (推定内訳)

3. 実測データから読み取れる CS の内訳

実測データから 1 request あたりの spinlock 実行回数を計算:

合計 CS 実行数 (90秒) / QPS × 90秒 = CS/req

1 req = 5 CS 実行 (N によらず一定)。 つまり Phase 1 で観察した CS 長分布は「1 req 内で 5 回発生する spinlock 保持時間の統計」であり、 item_lock 単独の値ではない。

4. 何が問題か

光の元の仮説を思い出す

元の仮説: 「N が極端に大きいと、他のスレッドが長時間 PAUSE 中の間に、 CS を実行中のスレッドが 1 リクエスト処理を完了し、再度 item_lock を獲得できる。 その結果 self-service パターン (1 スレッドが独占) が発生する。」

この仮説の検証には item_lock 単独の獲得パターン が必要:

  • item_lock は 単一 key ワークロード で 4 workers が奪い合う特定のロック
  • slabs_lock も 4 workers が奪い合うが、性質が異なる (グローバル、SET 時に多数呼ばれる)
  • 両者を混ぜて測ると、item_lock の self-service パターンが検出できない

具体的な問題

図 2: 混合計測では item_lock の独占が slabs_lock の均等分配で相殺されてしまう可能性

混合計測でも均等分布になった理由 (仮説)

Phase 1/2 で観察された per-thread 分布 25%/25%/25%/25% は以下の理由で説明可能:

  1. slabs_lock は SET のたびに呼ばれ、mutilate の 4 thread が対称に SET を送るので均等分配
  2. slabs_lock の呼び出し回数 (~4 CS/req) が item_lock (~1 CS/req) より多い
  3. 合算するとほぼ slabs_lock の分布に支配される → 均等に見える
  4. item_lock 単独では self-service パターンが発生していても、混合で埋もれる

5. 次のステップ: item_lock 単独測定

実装案

// spinlock.h に item_lock 専用の関数を追加

static inline void item_spinlock_lock(spinlock_t *sl) {
    for (int round = 0; round < 30; round++) {
        if (pthread_mutex_trylock(&sl->mutex) == 0) {
            tl_item_lock_start = _rdtsc();   ← item 専用の tsc
            return;
        }
        for (int p = 0; p < N; p++) cpu_relax();
    }
    pthread_mutex_lock(&sl->mutex);
    tl_item_lock_start = _rdtsc();
}

static inline void item_spinlock_unlock(spinlock_t *sl) {
    spinlock_record_item_hold(_rdtsc() - tl_item_lock_start);
    pthread_mutex_unlock(&sl->mutex);
}

そして thread.c の item_lock 使用箇所を書き換え:

// thread.c:136
- spinlock_lock(&item_locks[hv & hashmask(item_lock_hashpower)]);
+ item_spinlock_lock(&item_locks[hv & hashmask(item_lock_hashpower)]);

これで:

  • item_lock 用の rdtsc 計測とカウンタは hold_item_samples / hold_item_total_count
  • slabs_lock (既存の spinlock_lock/unlock を使う箇所) は既存の hold_samples
  • SIGUSR2 で両方を dump: hold_item_samples_thread<N>.bin, hold_slabs_samples_thread<N>.bin

実験プラン

  1. debug/hold-time-v2 に item_lock 分離パッチを追加 (小規模)
  2. ビルド → memcached_hold_split_debug
  3. Phase 1 と同じ条件で sweep 実行 (T=4, N sweep, ~97 分)
  4. item_lock 単独の per-thread 分布を確認
  5. もし偏りがあれば self-service 仮説が支持される
  6. 偏りがなければ、光の仮説は棄却 → 均等分配は真の統計的現象
