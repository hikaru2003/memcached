1. GET リクエストの全フロー

光の元の想定: 「GET リクエストが来る → キーのロック取得 → 値を読む → ロック解放 → クライアントへ返信」

実際の実装: 「値の読み取りはロック外」。以下が正確な流れ:

2. SET リクエストの全フロー

SET は 2 つのロックが順に登場する。GET 図と対応させて、各ステップを縦に並べて整理:

図 2: SET リクエストの全フロー (縦に整列)。青領域が slabs_lock、ピンク領域が item_lock、緑領域がロック外
重要な設計原則:
  • refcount-- と item_free は item_lock 内で実行
  • ただし refcount が 0 に ならない 場合 (誰かが read 中)、free せずそのまま抜ける
  • SET リクエストは待たずに STORED を返信
  • old_item の実際の free は「最後の参照者」が行う (= deferred free / 遅延解放)
重要な修正: refcount-- と item_free (もし発火するなら slabs_free まで) は item_lock 保持中に実行される。ロック外ではない。

SET は「アドレス書き換え」= new item を別アドレスに作る

図 2.5: SET は「新アドレス Y に new_item を作り、hash table のポインタを X→Y に書き換える」。old_item (アドレス X) は refcount で保持され、参照が消えたら slab に返却

2.5. SET は待たない — deferred free (遅延解放) 設計

SET が old_item を unlink する時、他 worker が old_item を read 中でも 待たずに完了する。詳細を追う:

コードの実際

void do_item_unlink(item *it, const uint32_t hv) {
    if ((it->it_flags & ITEM_LINKED) != 0) {   // ← まだ hash table にリンクされているか
        it->it_flags &= ~ITEM_LINKED;              // フラグを消す
        assoc_delete(...)                              // hash table から削除
        item_unlink_q(it)                              // LRU から削除
        do_item_remove(it)                             // ← refcount-- してみる
    }
}

void do_item_remove(item *it) {
    if (refcount_decr(it) == 0) {              // atomic 減算、結果が 0 なら
        item_free(it);                                 // slab に返却 (slabs_lock 取る)
    }
    // refcount ≠ 0 なら何もしない (待たない、そのまま return)
}

2 つの条件文の意味

条件意味なぜ必要
(it->it_flags & ITEM_LINKED) != 0「まだ hash table に登録されているか」
ビット AND で LINKED フラグを抽出		二重 unlink 防止 (別スレッドが既に削除済みなら何もしない)
refcount_decr(it) == 0「refcount を 1 減らして、結果が 0 か」
atomic 演算で減算		0 になった時だけ free (誰も参照してない = 安全に破棄可)

「以下を実行」の具体的な中身 (6 ステップ)

do_item_unlink の if ブロック内でやっていること全部:

void do_item_unlink(item *it, const uint32_t hv) {
    if ((it->it_flags & ITEM_LINKED) != 0) {
        ① it->it_flags &= ~ITEM_LINKED;          // LINKED フラグを消す
        STATS_LOCK();
        ② stats_state.curr_bytes -= ITEM_ntotal(it);  // stats: バイト数を減らす
           stats_state.curr_items -= 1;              // stats: item 数を減らす
        STATS_UNLOCK();
        ③ item_stats_sizes_remove(it);              // サイズ別統計から除外
        ④ assoc_delete(ITEM_key(it), it->nkey, hv);  // hash table から削除
        ⑤ item_unlink_q(it);                         // LRU リンクから外す
        ⑥ do_item_remove(it);                        // refcount--、0 なら item_free
    }
}
ステップ操作意味
①LINKED フラグを消す次に unlink されないようにマーク (二重削除防止の準備)
②stats のカウンタ更新memcached 全体の item 数・バイト数の統計
③サイズ別統計から除外size buckets の内部 stats
④hash table から削除hash_table[key] のエントリを消す = 以降 hash 経由でアクセス不可
⑤LRU リンクから外すLRU リスト (heads/tails) から削除、eviction 対象外
⑥refcount-- (0 なら item_free)参照カウント減算、0 なら実際にメモリ返却
要約: 「item を memcached の管理下から外す作業一式」。 特に ④ hash table 削除 と ⑤ LRU 削除 がメイン。 その後 ⑥ で refcount-- して 0 なら実解放、0 じゃなければ (誰か読んでるので) そのまま。

光の質問への回答 (追加分)

Q: 最後に参照を手放した人が削除するとのことだが、read している側は「これが古い値かどうか」を判断できるのか？

A: No、read 側は判断できない (そして memcached はそれを気にしない設計)。

詳細:
  • worker0 (GET) は item_A のポインタを取得したら、item_lock 解放後にそのまま value を read してレスポンス送信
  • この間、別スレッドが SET で item_A を unlink して LINKED フラグを消しても、worker0 は flags を再チェックしない
  • worker0 は「自分が掴んだ item の内容」をそのまま client に送る
  • その値が「memcached の最新値」かは worker0 には知る術がない

ただし以下は保証される:
  • ✅ メモリ安全性: read 中の item は refcount ≥ 1 なので絶対 free されない (dangling pointer なし)
  • ✅ データ整合性: item の value は immutable なので、read 中に内容が書き換わることはない
  • ❌ 最新性: 並列 SET 中に古い値を返す可能性あり (linearizability なし)

これは memcached の設計選択 (キャッシュとしての高スループット優先)。 「絶対に最新の値」が必要な用途 (残高管理など) には向かないが、 「多少古くても OK な高速キャッシュ」としては最適な設計。

コードで見ると GET は flags 再チェックしていない

// thread.c: GET の実装
item *item_get(const char *key, const size_t nkey, ...) {
    hv = hash(key, nkey);
    item_lock(hv);
    it = do_item_get(...);        // it_flags を確認して refcount++
    item_unlock(hv);
    return it;                     // ← ここでポインタを返す
}
// この後の read フローで it_flags は 一切再チェックされない
// 呼び出し元は it の value をそのまま client に送信する

refcount が 0 じゃない時のフロー

光の質問への直接回答

Q: refcount が 0 じゃない時、ゼロになるまで待つのか？
Q: SET リクエストの完了 (client への返信) は refcount 0 まで保留か？

A:
  • 待たない (待機コードは存在しない)
  • SET は refcount_decr してみて、0 じゃなければ「何もせず」item_unlock して STORED を送信
  • クライアントへの返信は 即座に 行われる (数十 cy 内)
  • old_item の実際の free は「最後に参照を手放した worker」が行う
  • これが memcached の高スループット設計の鍵: 「他スレッドを待たない」ことでロック保持時間を最小化

2.6. 「削除」の実体 — リンク削除とメモリ解放は別物

「最後に read した人が削除する」と説明したが、これは正確ではなかった。実際には 2 段階の「削除」 が存在し、 それぞれ別のスレッドが担当する。

2 つの「削除」の内訳

処理誰が実行いつ何をする
① hash table のリンク削除 (unlink)SET を実行した worker (worker1)SET の item_lock 内でassoc_delete で hash table から削除、LRU からも外す、LINKED フラグを消す
② 実メモリの解放 (item_free = slab 返却)最後に参照を手放した worker (worker0)GET の read 完了後、item_remove を呼んでrefcount-- して 0 になったら item_free → slab に返却
重要: 最後に read した worker は「リンク削除」は一切しない。 それは既に SET で完了済み。最後の read が担当するのは メモリ返却だけ。

タイムラインで見る (2 つの削除の区別)

図 2.9: リンク削除とメモリ解放は別の worker が別のタイミングで実行する

「最後だと判断する仕組み」= refcount_decr の戻り値

void do_item_remove(item *it) {
    if (refcount_decr(it) == 0) {   // ← 減算後の値が 0 なら「自分が最後」
        item_free(it);                     //   実際にメモリ返却
    }
    // 0 じゃなければ他にまだ参照者がいる → 何もしない
}

refcount_decr は atomic 演算 で、複数スレッドが同時に呼んでも 「1 を引いた後の値」を 自分だけ 見られる。 結果が 0 なら「自分が最後の参照者」= メモリ解放担当。 0 以外なら他がまだ持っている → 何もしない (次に参照を手放すスレッドに任せる)。

光の疑問への直接回答

Q: 最後に read した人が古い値を削除するとのことだが、最後に read が読んだ時にどうやってリンクを削除するの？

A: 最後の read はリンク削除を一切しない。

説明:
  • hash table の「リンク削除」= SET が既に完了させている (SET の item_lock 内で assoc_delete + item_unlink_q + LINKED フラグ消し)
  • 最後の read (= worker0 が item_remove を呼ぶ時) がやるのは メモリ解放 (slab へ返却) のみ
  • 「最後だ」の判断は refcount_decr() の戻り値が 0 かどうかで自動判定
  • この段階では既に hash table からは item は消えているので、リンク操作は不要

3. なぜロック外で読み書きしても安全か

光の疑問「値の読み書きがロック外って安全なの？」への答え。memcached の設計は以下の 2 つの仕組みで安全性を担保している:

仕組み A: item は immutable

  • 一度作られた item のデータ (value) は 絶対に書き換えない
  • SET で「値を変更」する時は、新しい item を作って hash table で置き換える
  • 古い item はそのまま残る (誰かが read 中の間は生き続ける)

仕組み B: refcount による寿命管理

  • GET で item を取得する時、refcount_incr(item) で参照カウント++
  • 参照カウントが 1 以上の間、item は 絶対に free されない
  • read が終わったら item_remove(item) で refcount--
  • refcount が 0 になったら その時に初めて slabs_free で解放
図 3: 同じ key に GET と SET が同時に来ても、refcount で古い item は保持される
結論: 「値の読み書きがロック外」= immutable + refcount のおかげで安全。 ロック保持時間を最小化することで、並列度を最大化している。

4. PAUSE で待っているのはどの部分か

PAUSE を挟むのは ロック取得試行 (spinlock_lock) の中:

static inline void spinlock_lock(spinlock_t *sl) {
    for (int round = 0; round < 30; round++) {
        if (pthread_mutex_trylock(&sl->mutex) == 0)   // trylock 試行
            return;                                       // 成功 → CS へ
        for (int p = 0; p < N; p++) {                  // 失敗
            cpu_relax();                                  // ← ここが PAUSE
        }
    }
    pthread_mutex_lock(&sl->mutex);                    // 30 回失敗 → futex 経由
}

つまり:

  1. 他 worker が item_lock を保持中に、worker0 が SET/GET で同じ item_lock を取ろうとする
  2. trylock 失敗 → N 個の PAUSE 実行 (待機)
  3. また trylock 試行 → 失敗 → 再度 PAUSE... を最大 30 回繰り返す
  4. 30 回失敗したら futex 経由でスリープ (これは最後の手段)

5. PAUSE で改善しようとしているのはどこの処理か

改善対象: item_lock の獲得競争 (図 1 の ③、図 2 の ② と ⑥)

具体的な改善内容:
  • N=0 (PAUSE なし): 30 回連続で trylock を叩く → cacheline A の pingpong 激しい → unlock latency 悪化
  • N を増やす: trylock 間隔が空く → cacheline A の pingpong 頻度減 → unlock latency 改善 → 全体 QPS 向上
  • N が大きすぎる: trylock 間隔が広すぎ → unlock 検知が遅れる → 待ち時間の絶対値が増える → 全体 QPS 悪化
どこかに 最適な N があり、それはロック競合の激しさ (= CS 内処理時間 × スレッド数) で決まる。

図 4: 4 workers が並列に動く様子。緑部分は全員同時に実行できる、赤/青部分は 1 worker のみ

比率で見ると

領域時間比率 (実測から推定)並列度
ロック外 (recv, parse, memcpy, read, send)大半 (95%+)4 workers 並列
item_lock 内 (hash table 操作)数%1 worker のみ
slabs_lock 内 (メモリ管理)数%1 worker のみ
要点: memcached は「ロック保持時間を最小化して並列度を最大化する」設計。 PAUSE で改善しようとしているのは、この 少ないロック競合部分での cacheline pingpong と待機効率 であって、 「値の読み書きの時間」ではない。

7. Consistency (一貫性) の話 - 更新前の値を読む可能性

「GET → SET → GET の順で送ると、2 回目の GET は更新前の値を読む可能性があるのか？」への回答。

ケース A: client が同期的に送る場合 (前の完了を待って次を送る)

t1: GET1  → server が "0" 返信
t2: (client は "0" を受け取ってから次を送る)
t3: SET(1) → server が "STORED" 返信
t4: (client は "STORED" を受け取ってから次を送る)
t5: GET2  → server が "1" 返信
このパターンでは GET2 は必ず "1" を返す。順序が守られている。

ケース B: 並列に送る場合 (mutilate の pipeline が実態)

GET2 が SET の完了を待たずに送信されると、SET と GET2 が memcached サーバー内で 並列に処理 される。この時、GET2 が古い値を返す可能性がある:

"0" を返す hash_table[key] は既に item_B を指しているが、worker0 は自分のポインタ経由で item_A を読んでいる
図 5: SET 完了後でも、SET 前に GET が item_A を「掴んで」いれば古い値を返す
結論: memcached は linearizability を保証しない。並列に SET と GET を送ると、GET が古い値を返すことがある。ただし client が同期的に (前の完了を待って) 送信すれば順序は守られる。

Consistency 保証の一覧

プロパティ保証説明
メモリ安全性 (use-after-free 等)✅ 保証refcount で item の寿命を管理
hash table の一貫性✅ 保証item_lock で書き換えを排他
client 内の順序保持 (sequential consistency 相当)✅ 保証client が同期送信すれば順序通り
並列 SET/GET の linearizability❌ 保証しないSET 完了後の GET が古い値を返す可能性

なぜこの設計なのか

  • memcached は キャッシュ なので、厳密な linearizability より スループット優先
  • ロック保持を最小化 (hash table 操作のみ) して並列度を最大化
  • immutable item + refcount で「壊れない」ことは保証、「最新である」ことは緩い
  • キャッシュとして使う限り、一時的に古い値が見えても問題ない (最終的には収束する)
  • 厳密な一貫性が必要な用途 (銀行残高など) には RDBMS などを使う

まとめ

  • 光の元の想定「ロック取って値を読み書きして解放」= 半分正しい
  • 正確には「ロック取ってメタデータ (hash table や refcount) 更新して即解放、値の read/write はロック外」
  • ロック外で安全な理由 = immutable item + refcount による寿命管理
  • PAUSE は item_lock/slabs_lock 取得試行の失敗時に挟む
  • PAUSE で改善しようとしているのは ロック cacheline の pingpong 頻度と unlock 検知遅延のバランス
  • 並列できるのは 95%+ (ロック外の処理)、排他される数% (CS 内) が競合ボトルネック
