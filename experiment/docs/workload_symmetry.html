memcached のリクエスト分散とワークロード対称性

「self-service パターン (1 コアがロックを独占する現象) は N が大きくなるほど発生する」という 仮説を検証するため、per-thread の CS 実行回数を実測したところ、 N によらず完全に均等分布 (25%/25%/25%/25%) になった。 これは self-service パターンが発生していないのではなく、 実験のワークロード設計上、そもそも発生し得ない ためである。 本資料はその仕組みを説明する。

1. memcached の接続割り当て (round-robin)

memcached は master-worker モデルで動く:

  • main thread (1 個) が listen socket で accept() を呼ぶ
  • 新しい接続を round-robin で worker thread に割り当てる (dispatch_conn_new)
  • 一度割り当てられた接続は その worker に永続的に固定される
  • 各 worker は自分の event loop で担当接続の request を処理する
図 1: memcached の接続割り当ては round-robin。以降その接続は特定の worker に固定

2. mutilate のスレッド・接続モデル

mutilate は負荷生成側:

mutilate -s 127.0.0.1:11222 -T 4 -c 1 -d 32 -r 1 -u 0.5 -t 30
  • -T 4 = 4 個の worker thread を起動
  • -c 1 = 各 worker が 1 個の接続を持つ
  • 合計 4 × 1 = 4 接続 が memcached に張られる
  • 各 mutilate thread はループで request を送信 (対称的なペースで)

3. 対称ワークロード vs 非対称ワークロード

図 2: 対称ワークロード (左) は必然的に均等分布、非対称ワークロード (右) は偏りが発生し得る

4. self-service パターンが発生する条件

光の仮説「N が大きくなると self-service パターン (1 コアがロックを独占) が発生する」を成立させるには:

  1. ロックを取ろうとする複数コアが同じデータを処理できる ← memcached の設計では NG (各接続は 1 worker に固定)
  2. または 同じ worker が高頻度でロックを取れる状況: 単一 worker に大量接続が集中する
今回の実験ワークロードでは条件 1 が満たされないため、たとえ N が大きくても self-service にはなり得ない。 各 worker は自分の担当接続からしか request を受けないので、他 worker の request を「横取り」できない。

重要な帰結:
  • 過去の全 N sweep 実験は 対称ワークロードで行っていた
  • この設計では self-service パターンは仕組み上発生しない
  • 実測で observed された per-thread 均等分布は「self-service が起きないこと」を示すのではなく、「そもそも起きようがないこと」を示す
  • 光の self-service 仮説は この実験では検証不可。仮説自体は棄却できない (未検証)
  • Approach A の T=2 / T=8 の解釈は、非対称性を考慮して再検討する必要があるかもしれない

6. self-service 仮説を検証するための実験案

非対称ワークロードを作って self-service パターンが N で誘発されるか見る:

案 A: 単一 mutilate thread + 多接続

mutilate -T 1 -c 16 -d 32 -r 1 -u 0.5 -t 30
# 1 mutilate thread が 16 接続を timeslice で切り替え
# memcached workers 4 個に 16 接続が round-robin で分散
# → 各 worker が 4 conns 担当だが、mutilate 側が 1 thread しかないので
#   ある瞬間は 1 conn しか active でない
# → active な conn の worker が単独で処理する時間帯が発生

案 B: 不均等な rate の mutilate threads

mutilate の負荷を各 thread で変えるには mutilate 側の改造が必要 (通常はすべて同一 rate)。

案 C: memcached の worker 数 > mutilate の実接続数

MC_THREADS=8, MUT_THREADS=1, MUT_CONNS=1
# memcached workers 8 個に接続 1 つだけ → 1 worker が独占的に処理
推奨: 案 A (単一 mutilate thread + 多接続) が最もクリーン。 mutilate 側の設定変更だけで完了し、負荷の集中パターンが N に依存するかを見られる。
