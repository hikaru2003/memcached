Closed-loop workload と pipeline back-pressure による自動収束

「per-thread 分布が均等になるのは誰が作用してるからなのか？」という光の質問への回答。 結論: 誰か特定のコンポーネントが調整しているわけではなく、closed-loop workload の pipeline depth 制約が back-pressure として自動的に作用している。

目次
  1. 前提: mutilate は closed-loop
  2. Pipeline depth (-d 32) の意味
  3. もし self-service (独占) が発生したら
  4. Pipeline 満杯 → 送信停止 → 独占が続かない
  5. 「自然な収束」の実体

1. 前提: mutilate は closed-loop

負荷生成側 (mutilate) には 2 通りのモードがある:

モード動作本実験
Open-loop時間ベースで request を送り続ける (rate を指定)。response 待たない❌ 使用してない
Closed-loop (pipeline)outstanding request が pipeline depth に達したら送信停止。response が返ったら次を送る✅ これを使用 (-d 32)

2. Pipeline depth (-d 32) の意味

mutilate 起動時のフラグ:

mutilate -T 4 -c 1 -d 32 ...

各 connection について:

  • mutilate は最大 32 個の request を outstanding (未応答) にできる
  • 32 個溜まったら response を受け取るまで送信停止
  • response が 1 個返ってきたら → 次の request を 1 個送信
図 1: Pipeline depth の意味。outstanding が 32 に達すると mutilate が送信を止める

時刻 t=0 で偶然 worker 0 が連続してロックを取り始めたと仮定する:

図 2: 独占状態が続くと、他 conn の pipeline が満杯になり mutilate 側の送信が停止する

4. Pipeline 満杯 → 送信停止 → 独占が続かない

5. 「自然な収束」の実体

誰が調整しているのか？: 誰も直接調整していない。 Pipeline depth 32 という物理的な制約 が、以下の連鎖を強制する:
  1. もし 1 worker が独占的に CS を回すと
  2. 他 worker の conn の outstanding request が積み上がる
  3. 32 個溜まったら mutilate が送信停止 (back-pressure)
  4. 独占 worker の conn も高速回転しているが 1 conn 分の request しかない
  5. 結局 1 conn の rate ≈ 250k QPS 程度で頭打ち
  6. この状態が続くと合計 QPS が下がる
  7. 一方、均等分配ができれば 4 conn 並列で 800-900k QPS 出る
  8. ロック排他の仕組み上、確率的に独占が長続きせず均等に近づく

もっと本質的な理由

実は「独占が発生しない」というよりも、独占が発生するとその状態を維持するインセンティブがない という方が正確:

  • ロックを取れる確率は「trylock を実行するタイミングで空いているか」で決まる
  • 4 workers 全員が同じ確率で spin phase の任意時点にいる (対称ワークロード)
  • ある瞬間に worker A が偶然連続で取れても、その次は他 worker が取る確率が高い (ランダム化)
  • 90 秒間の累積で「たまたま連続獲得」は特定 worker に偏らない
  • 結果、per-thread 分布は 25%/25%/25%/25% に自然に落ち着く
まとめ:
  • 「均等分配」は誰かが調整しているわけではない
  • 本質は 対称ワークロードでは全 workers が同じ確率でロックを取れる
  • もし偏りが発生すると pipeline back-pressure で合計 QPS が下がる → その状態が長続きしない
  • 結果、90 秒間の累積で観測される分布は自然に均等になる
