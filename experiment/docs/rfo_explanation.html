RFO (Read For Ownership) とは何か

memcached の実験で頻出する RFO について、なぜ発生するか、何を意味するか、 実験でどう計測しているかをまとめる。

1. 一言で言うと

RFO (Read For Ownership) = 「他コアが持っているキャッシュラインを、自分のコアで書き込むために M 権 (排他所有権) を取り直す要求」。

書き込み (store) の直前に発行される。多発すると コア間のキャッシュライン争奪 (バス競合) が激しいことを意味する。

2. なぜ RFO が必要か (MESI プロトコル)

Intel CPU は各キャッシュラインに MESI 状態を持たせている:

状態意味書き込み可能?
M (Modified)このコアだけが持ち、書き換え済み✅ 可
E (Exclusive)このコアだけが持ち、書き換え前✅ 可 (M に遷移)
S (Shared)複数コアが同一内容を持てる❌ 不可 (RFO 必要)
I (Invalid)無効❌ 不可 (RFO 必要)
ルール: キャッシュラインを書き換えるには M または E 状態で持つ必要がある。
S や I 状態の line に書き込もうとすると、RFO を発行して他コアの line を invalidate し、 自分が M 状態を取得しなければならない。

3. RFO の具体的な発生シナリオ

シナリオ A: 通常の atomic 変数への書き込み

// Core A で実行
counter++;   // 内部で: load counter → increment → store counter
             //         ↑ store 時に RFO 発行

もし counter の cacheline が他コアで S や I 状態なら、 Core A は RFO を発行して M 権を取る。

シナリオ B: LOCK CMPXCHG (spinlock の trylock)

// pthread_mutex_trylock の内部
lock cmpxchg mutex, ...   // atomic RMW (Read-Modify-Write)

LOCK-prefix 付き命令は 成功/失敗に関わらず 対象アドレスの cacheline を M 権で取ろうとする。つまり trylock 1 回 = RFO 1 回。

これが spinlock 実装で RFO が多発する理由: 30 rounds の trylock ループで、 成功するまで毎回 RFO を発行 → 他コアの cacheline を invalidate → pingpong 発生。

シナリオ C: memcached での RFO 発生源

1 リクエスト処理中に RFO が発生する主な箇所:

  1. spinlock_trylock() の LOCK CMPXCHG: 30 rounds まで繰り返し
  2. pthread_mutex_unlock() の atomic store: ロック解放時 1 回
  3. item の refcount 更新: refcount_incr / refcount_decr (atomic RMW)
  4. hash table のエントリ書き換え: SET 時の pointer update
  5. LRU list のリンク更新: item アクセスごと
  6. stats カウンタ: 各種統計の書き換え

4. RFO の測定方法

Intel の Performance Monitoring Unit (PMU) で計測可能:

アーキperf イベント名
Broadwell / Ice Lakeoffcore_requests.demand_rfo
Emerald Rapidsl2_rqsts.rfo_miss (offcore_requests.demand_rfo は N/A)
Skylake annoffcore_requests.demand_rfo
注意: demand_rfo は「L1/L2 でヒットしなかった RFO」を数える (offcore、つまり L3 以降へ問い合わせに行ったもの)。L1 hit RFO は含まない。 真の RFO 総数はもっと多いが、通常 offcore RFO が「他コアと争奪した回数」の指標になる。

5. 実験での RFO 解釈

RFO/req = 1 リクエストあたりの RFO 発行数

RFO/req = (総 RFO 数 / 総 request 数)

これが大きいほど、1 リクエスト処理中に他コアとの cacheline 争奪が多く発生している。

Skylake ann の実測値の例

NRFO/req解釈
0 (tight spin)6230 rounds の trylock + 他の atomic 操作でハイ
170 (ピーク)QPS が伸びるので RFO 総数も増える (RFO/req もわずかに増)
1050trylock 頻度減で RFO 減
20032大幅に減 (trylock 間隔が広い)

6. RFO と QPS の関係

一般に:
  • RFO 多 → cacheline pingpong 激しい → L2/L3 帯域圧迫、コアの stall 増 → QPS 悪化
  • RFO 少 → cacheline が安定 → QPS 良好
ただし memcached の spinlock 実験では RFO 減少と QPS 改善は完全には一致しない:
  • N=0 → N=200 で RFO は単調減少 (62→32)
  • しかし QPS 山形は N=4 でピークで、その後緩やかに悪化
  • → RFO 減少は QPS 改善の一因だが、唯一の要因ではない (他に unlock latency、handoff latency 等が絡む)

7. 「バス競合」との関係

「バス競合」は一般用語で、複数コアが同じキャッシュラインを奪い合う現象。 RFO はその 操作的な指標 (=書き込みのための M 権取得回数)。 RFO が多い = バス競合が多い、と読める。

厳密には:

  • RFO: 書き込み前の M 権取得要求 (回数)
  • HITM: 他コアの M state から自分に move された cacheline (受信側の指標)
  • バス帯域: 単位時間あたりの cacheline 移動量
